# 0007 - `typeSwitch` delegation helpers exist only for declared case keys, and nested calls overwrite `args.value`

> **Status:** Open
> **Severity:** Minor
> **Area:** `src/type/switch.ts`, `src/type/switchAsync.ts`, `src/array/wrapper/methods/select.ts`
> **Date opened:** 2026-11-04

## Context

`typeSwitch`'s headline feature is nested delegation: the object handed to a case
handler contains one callable per **case key**, so a handler can hand a
sub-value back to the dispatcher instead of re-entering it by hand —
`({ string, number }) => typeof x === 'string' ? string(x) : number(x)`. This is
how `arrayCreate` (`array/create.ts:48-64`), `jsonUpdate` (`json/update.ts:34-49`),
`objectMerge`, `dataClone`, `objectExtract`, `booleanPartial*` and the
`arrayWrapper` methods compose their type logic, and `knowledge.md` advertises it
as "the core dispatcher".

Two properties of how those helpers are built (`type/switch.ts:95-100`) leak into
every one of those call sites.

## Gap

**1. A helper exists only for a key the caller declared.** The args object is
built with `objectEach(cases, …)` — it iterates the *provided* cases, so
`args.<anyOtherType>` is `undefined`, not a dispatcher into `default`:

```ts
typeSwitch(1, {
    string: () => 'S',
    // no `number` key declared, but there IS a default
    default: ({ string }) => string(1),   // fine
});
// and the failure mode:
typeSwitch(1, {
    string: () => 'S',
    default: () => 'D',
});
// a handler that calls args.number(1) → TypeError: args.number is not a function
```

So the delegation surface is "whatever keys you happened to declare", while
`knowledge.md` presents the case set (`string | number | boolean | object | array
| function | undefined | null | default`) as if it were always available. A
handler written for one cases object breaks when moved to a narrower one, and the
failure is a `TypeError` from inside the dispatcher rather than the `default`
answer the caller wrote.

**2. Nested delegation cannot see the parent value.** `:94` sets
`args.value = input`, and `:97` invokes the delegated handler with
`{ ...args, value: val }`. The parent value is therefore *replaced*, not
preserved: a nested handler that wants both the sub-value and the original value
has no way to get the original. Every consumer that needs the parent context
closes over it manually instead (e.g. `array/wrapper/methods/keys.ts:84-92`,
which re-binds `number`/`string`/`boolean` rather than reading a parent value).

**3. Static (non-function) case values explode when delegated to.** `:97` calls
`caseHandler?.({ … })`, and `?.` only guards `null`/`undefined`. A cases object
mixing static values and callbacks — legal at the top level, because `:103`
returns the raw value — throws `TypeError` when reached through a helper.
`src/type/switch.test.ts` now pins the raw-value path and this helper path
separately.

**4. Same shape in the async twin.** `src/type/switchAsync.ts` mirrors all three
properties (its own handler loop awaits the same way), so fixing one file without
the other splits the pair.

**5. Downstream crash.** This is the proximate cause of the `select` bug in
[0005](./0005-array-wrapper-filter-sharing.md): `array/wrapper/methods/select.ts:59`
destructures `string`/`boolean` helpers from an outer cases object that declares
only `number`/`array`/`default`, so `select(['apple'])` throws `TypeError` lazily
at filter-evaluation time (`:63-64`).

## Why it is the way it is

Building helpers from `cases` is what makes the pattern cheap and open-ended: any
domain-specific key works (`objectSwitch` and `stringSwitch` use the same trick
with their own key sets, `object/switch.ts:53`, `string/switch.ts:52-63`), and a
fixed set of eight helpers would not extend to custom type names
(`'date'`, `'map'`, a class name). The `?.` at `:97` shows the author was thinking
about a *missing* key rather than a *non-callable* one.

Overwriting `value` is also load-bearing: it is what makes `string(x)` dispatch
`x` rather than the parent value. The gap is only that the parent value has no
place to live.

## Evidence

- `src/type/switch.ts:94` — `const args: any = { value: input };`
- `src/type/switch.ts:95-100` — helpers generated by iterating `cases`
  (`objectEach(cases, …)`), one per declared key, each calling
  `caseHandler?.({ ...args, value: val })`.
- `src/type/switch.ts:91,103` — top-level match falls back to `default`, and a
  non-function case value is returned raw. Both behaviors differ from the helper
  path.
- `src/type/switchAsync.ts` — same construction, awaited.
- `src/array/wrapper/methods/select.ts:59-65` — real in-package consumer that
  destructures undeclared helpers and crashes.
- `src/array/wrapper/methods/keys.ts:84-92` — a consumer that works only because
  it declares `number`/`boolean`/`string` at the top level (`:46-82`).
- Pinning tests: `src/type/switch.test.ts` (full 9-branch matrix, raw non-function
  values, the `args.<undeclared>` `TypeError`, value-replacement chain
  `S:B`), `src/type/switchAsync.test.ts` (mirrors plus the async-only cases).

## Proposal

1. Materialize the canonical type-name helpers unconditionally, not from
   `cases`: for each of
   `string | number | boolean | object | array | function | undefined | null`
   bind `args[t] = (val) => typeSwitch(val, cases)` — which routes through the
   normal match-or-`default` logic at `:91` — instead of calling the case handler
   directly. Undeclared keys then land on `default` (the documented behavior)
   rather than throwing, and *declared* keys keep working because `typeSwitch`
   will find them.
2. Keep every key the caller declared as an extra helper (custom type names and
   the `default` key), so the extensibility property is preserved.
3. Preserve the parent value under a distinct key — `args.parentValue` (or
   `args.input`) — and leave `args.value` as the delegated value; the current
   overwrite is then a documented rule rather than a lost field.
4. Replace `caseHandler?.(…)` at `:97` with a callable check that routes a
   non-callable case value to `default`, matching the top-level rule at `:103`.
5. Apply the identical change to `type/switchAsync.ts`.

Alternatives considered and rejected:

- **Document "only declared keys are delegable" and leave the code.** Cheapest,
  and acceptable if the package prefers zero behavior change. It leaves the
  `select` crash to be fixed at the call site, and every future nested dispatch
  must remember the rule.
- **Freeze a single canonical helper set and forbid custom keys.** Breaks
  `objectSwitch`/`stringSwitch` symmetry and the class-instance dispatch that
  `typeName` already produces (`is/object.ts`, `data/clone.ts` rely on custom
  names falling to `default`).

## Acceptance criteria

- `args.<type>(val)` never throws for a canonical type name, declared or not; an
  undeclared name resolves through `default`.
- A handler can read the parent value after delegation (new key), and the
  delegated value still arrives as `args.value`.
- Delegating to a static (non-function) case value behaves like the top-level
  rule at `:103`.
- `typeSwitch` and `typeSwitchAsync` remain behaviorally identical apart from
  awaiting.
- `array/wrapper/methods/select.ts` either stops destructuring undeclared helpers
  or starts declaring them (cross-reference 0005).

## Tests to add

`src/type/switch.test.ts` and `src/type/switchAsync.test.ts`:

- flip the `args.<undeclaredType>(…)` `TypeError` case to an exact `default`
  result;
- new: delegation to a canonical helper that the cases object does not declare
  (e.g. `cases = { string: …, default: … }`, handler calls `args.number(2)` →
  `default` receives `value: 2`);
- new: parent-value visibility after one and two levels of nesting;
- new: static case value reached through a helper;
- keep the 9-branch matrix and the raw-value returns unchanged.
